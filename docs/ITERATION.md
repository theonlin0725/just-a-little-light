> 这份日志按真实顺序把两者拼起来，并记录每一轮的判断、改动、证据和遗留问题。

## 第 1 轮：36 关，先把「3 秒」立起来

**触发**

第一版全亮即通关，玩家快速来回拖动就能碰巧过关。

**判断**

> 「目前玩家只要快速、反复拖动，就可能在目标同时亮起的瞬间直接通关，解谜感不足。」
>
> 「不要简单通过限制拖动次数或惩罚操作来防『狂拉』，应主要依靠关卡机制和持续判定提升玩法深度。」

**改动**

- 通关条件改为「所有目标同时亮起 + 连续保持 3 秒」。
- 中断立即清零，不累计、不分别计时。
- 36 关，分六个阶段：基础、静态遮挡、移动障碍、干扰角色、双光源、综合。
- 三处进度反馈：水晶、光源外圈、底部进度条。
- 提示分三级：方向免费、移除障碍/给位置看广告。
- 通关分享卡、移动距离挑战、生成器与校验器。

**结果**

- 36 关全部可解；开局不会自动通关。
- 玩家开始需要「观察 → 站位 → 守住」，而不是「扫过去」。
- 代价：新手需要教学；第 1 关的解释成本变高。

**遗留**

- 关卡数量到 36 关后，玩法的后半程不够；需要新的机制维度。

## 第 2 轮：60 关、双侧水晶、皮肤、移除障碍

**触发**

36 关的机制已经用尽：单光源、单侧目标、静态/移动/干扰。再堆同类关卡只会重复。

**判断**

- 需要一个新的空间维度：**双侧水晶**，让「上下/左右都要亮」成为新的约束。
- 需要一个新的商业位置：**皮肤**，让广告卖表达而不是卖强度。
- 需要一个新的提示方式：**让玩家自己选一个障碍移除**，比「系统告诉你哪块挡」更有掌控感。

**改动**

1. **关卡 36 → 60**
   - 37–40 双侧教学；41–44 双侧静态；45–48 双侧 + 移动；49–52 双灯 + 双侧 + 移动；53–56 干扰；57–60 综合。
   - 所有关卡统一 3 秒，没有「13 秒」特殊规则。
   - 每关都能用默认光源、不看广告、不移除障碍通关。
2. **双光源与双侧水晶区分**
   - 双光源 = 场上两盏可拖的灯；双侧水晶 = 两面墙都有目标。
   - 第 49 关起两者叠加。
   - 第 27 关有「一颗水晶要两盏灯同时照」的双点标记。
3. **皮肤系统**
   - 4 款：初心（默认）、青焰、赤潮、星砂（看广告解锁）。
   - 可预览未解锁皮肤；解锁/装备持久化。
   - 皮肤只改绘制，不改照明范围、遮挡、判定、解区；测试逐帧对比亮灭序列。
4. **提示第二级改成「移除一个障碍」**
   - 进入移除模式后，所有可移除障碍描虚线；点谁选谁，可换目标或取消。
   - 静态挡板、移动挡板、干扰角色都能移除；墙、光源、水晶不能。
   - 移除同时作用于画面和真实遮挡判定；只看当前这一局，重开恢复。
5. **底栏五图标**
   - 选关 → 重来 → 提示 → 皮肤 → 首页。
   - 修复「选关点了没反应」：命中坐标与画面坐标不一致、拖动事件抢点击。
6. **改名**
   - 《投影》→《光影躲猫猫》→《就差一点光》。
   - 「光影躲猫猫」会让人以为是捉迷藏；「就差一点光」更贴近 2.9 秒的体验。

**证据**

- 60 关可解；双侧目标参与真实投影与判定，不是只画在另一边。
- 测试 186 项；微信包 89 KB；`npm run verify:wechat` 18 项。
- 第 37 关解区约占可拖拽区 3/4（双侧教学首关，故意宽容）；第 38 关起收窄到 8%–33%。

**遗留**

- 真机打开后画面缩在左上角；第 1 关拖动附近卡死；光效「抽搐」。
- 这些问题在浏览器与 API 替身里都看不到，必须真机/微信环境。

## 第 3 轮：稳定性，先让游戏「不死」

**触发**

真机反馈：导入开发者工具后手机打开无响应；修过一次后，第 1 关即将移动光圈时又卡死。同时 720×1280 首页缩在屏幕左上，右侧和下方大面积空白。

**判断**

这不是「性能差」，而是几个确定的工程缺口。先保命，再谈体验。

**改动**

| 问题 | 根因 | 修复 |
| --- | --- | --- |
| 首关拖动卡死 | `game.update()` 与画布调用在 `try` 之外，任一异常会让 RAF 链停止 | 帧级错误边界；更新/渲染分阶段；唯一循环调度器；连续失败熔断 |
| 音效异常外溢 | `tone()` 没有能力校验；`osc.connect(g).connect(...)` 假设返回可连接节点 | 分开 connect；初始化成功后再发布 ctx；失败静音降级；处理 Promise 拒绝 |
| 结算重玩崩溃 | `restart()` 没把 phase 改回 play，`drawWin` 读 null | 恢复合法 play 状态，清理拖动/移除/按钮/旧回调 |
| 渲染异常后状态泄漏 | save/restore 不配对，catch 只 setTransform，不清 clip | 有界状态管理；失败后回退最小绘制；限次重试 |
| 正式包渲染失败只清黑 | 缺少用户恢复路径 | 保留错误码与重试入口；失败帧不累计进度 |
| 提示求解堵主线程 | 输入回调里同步网格扫描，第 59/60 关约 180ms | 分片/预算/可取消（本轮未完全解决） |
| 画布左上角 | 视口只按逻辑尺寸缩放，没有统一 DPR/安全区/胶囊 | 三套坐标统一到 `viewport.js`；初始化和 resize 都刷新 |
| 低帧率下 3 秒变慢 | 每帧 dt 被截断 | 固定步长推进，仿真时间仍等于真实时间 |

**证据**

- 故障注入：音频 `createOscillator()` 抛错，主循环仍继续；渲染连续抛错，save 深度不增长。
- `npm run validate` 60/60；真机栏明确标「未测」（逐关交互回放是后面才补的）。
- 基线：release buildId `f9343d7936d3`，89 KB；QA `ada2efd53365`。

**遗留**

- BUG-07（提示求解未分片）仍在：第 59/60 关可能有一次约 180ms 卡顿。
- 真机卡死的根因没有 100% 复现，只是把「单点异常杀死 RAF」的路径堵住了。

## 第 4 轮：右手、时钟、声音、引导

**触发**

用户能真机游玩后，提了四项反馈：

1. 前期关卡主要在左边拖光球，右手不顺手；
2. 光点/光效「抽搐」，动效不顺；
3. 太安静，要低干扰 BGM、水晶「叮」、保持时的「滋滋」；
4. 多次读秒失败后，想要一个不打扰的灯泡引导。

**判断**

- **右手**：1–24 关做完整水平镜像，目标在左、操作在右；25–60 关不动，避免改变双灯/双侧布局。
- **抽搐**：先查时间单位，不要用删粒子掩盖。最终定位到微信端把 RAF 毫秒当秒传给渲染，相位速度放大 1000 倍。
- **声音**：BGM 不能是低频嗡鸣；要有旋律、有呼吸。音效要分三层：叮、蓄力、通关。
- **引导**：不能自动播广告，不能冻结关卡，不能抢手势；只在「第 5 次有效失败」后出现，指向真实灯泡。

**改动**

1. **镜像 1–24**
   - `mirror.js` 纯函数：光源 start/goal、水晶、挡板、移动轨迹、局部形状、bounds、墙几何全部反射。
   - 反射轴 `x=360`；右墙 582 精确变成 138。
   - 清掉 `_path` 预编译缓存，否则镜像后仍按旧坐标运动。
   - 25–60 关逐字节未变。
2. **时钟**
   - `clock.js`：视觉时间只用秒，单调累计，单帧限幅 50ms，后台/暂停冻结。
   - `draw(ctx, game, clock.time)` 两端统一；结算淡入改用游戏时钟。
   - 画质开关 `shadows / trails / beams` 真正接线。
3. **音频**
   - BGM：程序化 pad，三个低音正弦 + 低通 + 0.125Hz 呼吸，音量 0.045，3 秒淡入（第 5 轮改成五声音阶琶音）。
   - 水晶「叮」：状态从未亮到亮时触发一次。
   - 蓄力「滋滋」：带限噪声常驻循环，`setHold(k)` 只调参数，不新建振荡器；中断 60ms 淡出。
   - 音乐/音效两个开关，偏好写存档。
4. **灯泡引导**
   - 有效失败定义：全亮 → 保持 ≥0.3 秒 → 熄灭且未通关。
   - 第 5 次触发；默认显示 6 秒；每局 1 次、同关会话 2 次、重开 60 秒冷却。
   - 底栏真实灯泡外圈呼吸 + 浮动箭头 + 非模态文案；不复制假按钮，不冻结，不吞触摸。
   - 拖动中挂起，松手后显示；已开始新的有效保持则取消。

**证据**

- `npm test` 455 项，0 失败；60/60 交互层通关。
- `npm run validate` 60/60；微信包 102.1 KB；`npm run test:wx` 35/35。
- 镜像测试 76 项，含 168 组随机位置/时刻点亮序列一致。

**遗留**

- 真机未测：镜像后右手手感、BGM 是否可听、引导时机是否挡视线。
- BUG-07 仍在。

## 第 5 轮：上下布局、拉开光柱、重做前三关

这一轮在 changelog 里分成 ROUND3 和 ROUND4，但目标是连着的：**减少手指遮挡，把画面用满。**

### 5.1 全关卡旋转 90°

**触发**

> 「当前墙面光柱与水晶主要位于左右两侧，玩家从屏幕两侧操作时容易遮住目标和光路。」

**判断**

只镜像不够，只要目标和光源在同一水平线上，手掌就会压住光路。把玩法世界旋转 90°，让目标在上、光源在下。

**改动**

- 三层分离：背景层按 cover 铺满；玩法层旋转后放进 720×448 的玩法带；UI 层保持 contain，不旋转。
- 单侧关自动选旋转方向，让目标墙落在玩法带上沿；双侧关天然是上下两面墙。
- 触摸：先判断是否落在玩法带内，再逆变换回逻辑坐标；底部按钮仍用屏幕坐标。
- 方向键微调、方向提示、教学文案（「左右两侧」→「上下两侧」）同步。
- 双光源身份牌 1/2；双点水晶标记与 `1/2` 进度。

**证据**

- 60/60 关用真实触摸事件（经旋转逆变换）通关。
- `layout.test.mjs` 覆盖坐标往返、带内命中、方向映射、60 关渲染冒烟。
- 微信包 105.5 KB。

### 5.2 拉开光柱

**触发**

旋转后，上下两条墙离得太近，玩法带只占中间一小条。

**判断**

> 「光柱间距可以带动关卡几何布局调整，但要重新校验难度。」

**改动**

1. 沿墙压缩到 0.75（仿射变换，遮挡/点亮关系不变）。
2. 可拖拽范围从整面墙收紧到「本关内容 ±96」。
3. 按内容框定布局，缩放从 0.76 提到约 1.15。

**结果**

| 指标 | 之前 | 现在 |
| --- | --- | --- |
| 双侧关两墙距离 | 388 | 469–509，平均 480（+24%） |
| 单侧关玩法带高度 | 448 | 394–581，平均 489 |
| 手机上两墙距离（844 高） | 256 CSS px | 317 CSS px（+24%，最大 +31%） |

**代价**

- 距离挑战的「理论最优」不再可比；本轮把 `distance` 置空，第 6 轮才补回来。
- 只重做了第 1–3 关；其余关卡的「解法相似」问题没有系统解决。

### 5.3 第 1–3 关重做

审查发现三关的解都在 x 150–200、y 620–860 一带，都是「从右下往左上挪一点」，只是水晶数量不同。

| 关卡 | 原来 | 现在 | 玩家要换的动作 |
| --- | --- | --- | --- |
| 1 初次投光 | 水晶 y=470，解 (200,780) | 保持 | 直接拖到水晶方向，建立「拖光→亮」的直觉 |
| 2 一线天 | 水晶 y=430，解 (160,860) | 水晶 y=1000，解 (150,320)，挡板加高到 260 | 目标在墙的另一端，必须远离水晶、往上走，还要避开高挡板 |
| 3 双星 | 水晶 340/900，解 (180,620) | 水晶 300/980，解 (250,640)，挡板 160×120 | 两颗目标一上一下，找同时照顾两端的位置 |

重生成后只有第 2、3 关数据变化，其余 58 关逐字节未变。

**证据**

- 471 项测试，0 失败；60/60 交互层通关。
- 微信包 107.9 KB，buildId `9b3cebfebcc7`。

**遗留**

- 真机未测：两墙拉开后的手指遮挡、拖拽舒适度、长屏/刘海机的空间感。
- BUG-07 仍在。

## 第 6 轮：全量审查，承认「能过 ≠ 好玩」

**触发**

第 5 轮结束后，我自己连着玩，发现很多关是同一个动作。上一轮「只重做第 1–3 关」不够。

**判断**

> 「可解不等于解法有差异，也不等于难度不变。」
>
> 「玩家用几乎相同的动作就能连续过关。」
>
> 「不靠随机坐标、换皮肤、改名称、简单镜像或缩小解区制造差异。」

**改动**

1. **审查运行时关卡，不看原始数据**
   - 新增 `scripts/audit-levels.mjs`：机制标签、可行解区、可达距离、动作向量、保持窗口、相邻相似度。
   - 对象是镜像 → 沿墙压缩 → 边界收紧之后的最终关卡。
2. **重设计 7 关**（4/7/8/10/11/13/14），加上第 2、3 关，共 9 关。
   - 例：第 7 关原来和上一关一样往下挪，改后解区到上端，动作向量余弦从 1.00 变成 -0.83。
   - 第 8 关解贴到墙边最下端，必须离墙近才漏得过。
   - 第 11 关四目标的解放到最上端，走长对角。
3. **距离挑战回归**
   - 把沿墙压缩移进生成器，在算距离之前执行；运行时不再二次压缩。
   - 恢复 `distance` 字段，标签从「理论最优」改成「参考距离」（离散网格近似，不宣称严格最优）。
   - 第 5 关 196.3 / 第 9 关 185.0 / 第 12 关 274.6。

**证据**

- `npm test` 471 项，0 失败；60/60 交互层通关。
- `npm run validate` 60/60；微信包 107.7 KB，buildId `d41bb877a15d`；QA 189.6 KB，buildId `442ef94edcef`。
- 审查表：`docs/audit/LEVEL-AUDIT.md`；逐关记录：`docs/audit/PLAYTHROUGH-60.md`。

**遗留**

1. 25–36、38–53 的双光源/混合关只做了人工筛查，没有逐对改良；相似度指标只看第 1 盏灯的方向，不足以判断「分工/顺序」。
2. 第 4 关改良效果缺少前后对比截图。
3. 光源贴边时，光晕会被裁掉一部分（第 8 关最明显）。
4. 真机未测：改良关的实际手感、遮挡、难度感受。
5. 真机广告、体验版、好友排行都还没做。

## 这一路做对了什么

1. **先改规则，再改关卡。** 3 秒立住之后，所有机制才有意义。
2. **先保命，再谈体验。** 稳定性轮次没有新增玩法，但没有它，后面全是空谈。
3. **先让手不挡眼睛，再谈难度。** 镜像和旋转都是「让玩家看得见」，不是「让游戏更好看」。
4. **用测试守住下限，用审查挑战上限。** 471 项断言证明可解；审查脚本证明不重复；最后还得人玩。
5. **商业化边界前置。** 皮肤只改外观、广告不挡路，这两条如果晚定，后面会反复返工。

## 如果重来

- 先做 30 关，跑通每日一关和货币系统，再扩内容。
- 生成器完成后立刻做相似度审查，不要等 60 关都做完。
- 真机测试从第 1 关就开始，不要等浏览器「看起来没问题」。
- 不要用「测试全绿」当发布标准；测试只证明它没坏，不证明它好玩。
